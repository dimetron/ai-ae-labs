> **Одна пастка, яка коштує 20 хвилин.** `session.Event.Actions` — це **значення** типу `session.EventActions`, а не вказівник. Перевірка `if event.Actions != nil` **не компілюється**: `invalid operation: mismatched types session.EventActions and untyped nil` (перевірено компілятором 27.08.2026 на піні v2.2.0, перепеврено 13.09.2026 на v2.4.0). Правильно — `if len(event.Actions.StateDelta) > 0`.

## Легенда

Ваш агент — геній із амнезією: щойно ви закриваєте сесію, він забуває все. Research Agent так не може: він має пам'ятати, які теми ви вже досліджували і які джерела вам подобаються. Після Вебінару 9 Оксана з LEDGERWORKS отримала `memory_agent` із двошаровою пам'яттю — і тепер ваша черга: дати агенту пам'ять **між сесіями в одному підключеному memory-сервісі** й event log, який можна показати аудитору. `InMemoryService` не переживає перезапуск процесу: persistence — наступний production-крок, не прихована вимога цього ДЗ.

**Ключова ідея:** оновлення стану в ADK 2.0 залишає **дельту в event log** (`event.Actions.StateDelta`), яку можна інспектувати й відтворювати. `InMemoryService` захищає доступ від data race, але два записи в один ключ потребують окремої бізнес-логіки конфлікту.

## Якщо щось не працює

Перевірте це перед тим, як питати на форумі.

| Симптом | Найімовірніша причина | Що зробити |
|---|---|---|
| `go build` падає з помилкою версії | Go старіший за 1.27 (пін у `courses/AI_Agents_Engineering/lectures/go.mod`) | `go version`; оновіть Go до версії з go.mod |
| `event.Actions != nil` не компілюється | `Actions` — значення `session.EventActions`, не вказівник | замініть на `len(event.Actions.StateDelta) > 0` |
| `session.NewEvent("inv")` не компілюється: «not enough arguments» | у v2.4.0 сигнатура — `NewEvent(ctx, invocationID)` | передайте `ctx` першим аргументом |
| Агент стартує, але кожна відповідь — помилка API | Немає/невалідний `GOOGLE_API_KEY` | `echo $GOOGLE_API_KEY`; ключ має бути в оточенні процесу, не лише в `.env` |

| Факти «зникли» після перезапуску `go run` | Це очікувано: `InMemoryService` процес-локальний | Persistence — наступний production-крок, не вимога ДЗ; опишіть це в README |

## Основне завдання (до 80 балів)

**Ваше завдання —** дати агенту `memory_agent` пам'ять, яка переживає сесію: підключений `memory`-сервіс, факт, що відтворюється в другій сесії, і event log, придатний для аудиту. Додайте агенту `Event-Sourced Agent Memory`, стартуючи з [`courses/AI_Agents_Engineering/lectures/week5/Day9_Agent_Memory_Event_Sourced_State/labs/main.go`](labs/main.go):

1. **Сценарій «з амнезією і без»** за зразком `examples/tools/loadmemory/main.go`:
   - Створіть програмно першу сесію через `session.InMemoryService().Create(...)`.
   - Наповніть її щонайменше 3 повідомленнями користувача (наприклад: «інтеграція мерчанта — legacy», «рекомендований шлях — legacy-фікс», «не пропонуй новий API»).
   - Викличте `memoryService.AddSessionToMemory(ctx, previousSession)`.
   - Створіть другу сесію того ж `userID` — у ній `preloadmemorytool` уже подасть факти в контекст.
   - Запустіть `runner.Run(...)` у другій сесії з питанням «що порадити мерчанту A-114?» і зафіксуйте відповідь. Успіх — агент **не** радить новий API.

2. **Кастомний інструмент `remember_fact`** (уже наявний у стартері як `FactInput`/`FactOutput` — перевірте логіку):
   - Приймає `key` + `value`.
   - Пише у стан через `ctx.Session().State().Set("user:"+in.Key, in.Value)`.
   - Префікс `user:` — критичний: факт про **користувача** спільний для сесій того самого `userID` в одному `appName`; `app:` спільний для апки, а `temp:` відкидається після поточного invocation. Сам `InMemoryService` не переживає рестарт процесу.

3. **Інспекція event log:**
   - У `runner.Run` перебирайте `event.Actions.StateDelta`.
   - Збирайте дельти в буфер (наприклад, `[]map[string]any` із `ts` / `key` / `value`).
   - Після завершення сесії запишіть `audit_<user>_<sessionID>.json` через `json.MarshalIndent` і `os.WriteFile`.
   - Цей файл — **обов'язковий артефакт** для оцінювання (див. критерії).

4. **README з двома прогонами:**
   - Прогін А (stateless, для контрасту): тимчасово закоментуйте `MemoryService` у `runner.Config` — покажіть, що друга сесія не пам'ятає.
   - Прогін Б (memory-агент): з увімкненим `MemoryService` — покажіть, що пам'ятає.
   - Вставте фрагмент `audit_*.json` у README: «ось що змінилось у стані між 10:00 і 10:15».

5. **Розбір «бюджету контексту» одного кроку в README:**
   - Таблиця з 4 колонками: компонент (інструкції / preloaded memory / retrieval / історія), приблизний розмір у токенах, джерело.
   - Поясніть, чому обрали саме такі ліміти: чому N=5 фактів у preloaded, чому truncation в історії, чому instruction фіксована.

## Альтернативні теми (на вибір, оцінюються за тими самими критеріями)

Та сама механіка (дві сесії + memory-сервіс + явний інструмент запису + event log), інший домен:

- **Security:** агент-аудитор пам'ятає прийняті рішення — «цю CVE ми вже розглянули й ризик прийняли» — і не піднімає її вдруге. Ключі: `user:reviewed_cves`, `user:accepted_risks`.
- **Research:** Research Agent пам'ятає досліджені теми та улюблені джерела користувача, у другій сесії продовжує з того місця. Ключі: `user:researched_topics`, `user:preferred_sources`.
- **Fun:** бариста пам'ятає «як завжди»: улюблене замовлення і непереносимість лактози з минулої сесії. Ключі: `user:favorite_order`, `user:allergies`.

> **Слайд-попередження:** всі альтернативні теми — це **та сама архітектура**, інша лексика ключів стану. Не ускладнюйте — зосередьтеся на event log і двох сесіях.

## ++ Advanced (до 20 балів, для сеньйорів)

- **Тест конкурентної консолідації** (`TestStateDelta_ConcurrentConsolidation`): ≥10 паралельних goroutine-ів пишуть у **різні** ключі `user:worker:<i>` і тест перевіряє, що всі 10 значень доступні. Запускайте `go test -race ./...`. Це перевіряє відсутність data race для in-memory реалізації, але не робить одночасні записи в один ключ «магічно» merge-safe: для лічильника/балансу потрібен окремий atomic або транзакційний дизайн.
- **Аналіз (5–7 речень):** за якого критерію ваша задача потребувала б зовнішнього memory-сервісу (mem0 / Letta / Postgres + event log) замість вбудованого `InMemoryService`. Посилання на 4 критерії з Блоку 4 лекції (розмір / latency / multi-process / cross-session knowledge). Без аналізу — лише код — бали не зараховуються.

## 🔥 Бонус-трек (не оцінюється, не потрібен для сертифіката): Go OpenWiki Mini

Якщо у вас є час і натхнення — зробіть мінімальний repo-documentation workflow на Go (див. деталі в Лекції, розділ `🔥 Бонус-трек: Go OpenWiki Mini`):

- `docs/wiki/index.md` генерується детерміністично.
- `docs/wiki/log.md` — append-only журнал.
- Код репозиторію — read-only. Mutable surface — лише `docs/wiki/**` + посилання в `AGENTS.md`.
- Повторний запуск без змін — idempotent (bytes-equal `index.md`).

Це — той самий принцип event-sourced, тільки застосований до `git diff`. **Не додає балів і не є передумовою сертифіката**; це extra-hard портфоліо-артефакт для тих, хто хоче продовжити.
