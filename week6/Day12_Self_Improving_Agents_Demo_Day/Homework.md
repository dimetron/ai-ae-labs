# Практичне завдання 12 — Фінал: Personal Research Agent, який покращує сам себе

## Легенда

Шість тижнів тому це був стажер, що вмів гуглити план на вихідні. Сьогодні у вас є всі органи: травна система (ingestion, ДЗ 5), пошукове ядро (retrieval, ДЗ 6), стійкі до збоїв руки (harness, ДЗ 8), пам'ять (ДЗ 9), команда з делегуванням і HITL (ДЗ 10) та цикл критиків (ДЗ 11). Час зшити з них **Personal Research Agent** — і навчити його безпечно покращувати самого себе за принципами `autoresearch`. Це — **фінальний портфоліо-артефакт** курсу; те, що ви покажете на співбесіді або на демо-дні.

> **Чесне застереження перед стартом (з лекції, варто перечитати):**
> `autoresearch` — **research toy**, не enterprise-паттерн «як є». Патерн — серйозний (5 принципів, verifiability constraint, auditable trail), але Karpathy чесно пише в README свого репо, що це іграшка. Geoffrey Huntley показав, що unattended-ітерація може тривати місяці; це не є доказом контрольованого бюджету, відтворюваності чи production-безпеки. До продакшну вашому агенту буде потрібна **ізоляція, ідентичність, durable execution** — це вже за межами цього курсу. У цьому ДЗ ми збираємо **research-grade прототип**, який доводить, що патерн працює; production-hardened версію зберемо пізніше.

## Ранній win: перший видимий результат за ≤15 хвилин

Перший видимий результат — до того, як ви напишете хоч рядок власного коду. Стартовий шаблон — скелет без LLM, він запускається без ключа.

**Крок 0 (одна команда, ~1 хв) — L1-прогін із лекції.** Це той самий доказ, який показували на сцені: цикл вимірює кандидата й записує вердикт, не змінюючи нічого.

```bash
cd courses/AI_Agents_Engineering/lectures
go run ./week6/Day12_Self_Improving_Agents_Demo_Day/labs/solution --report-only
```

**Чекпойнт:** у виводі є `вердикт : would_keep`, метрика `1000.0 → 1180.0`, і рядок «`strategy.md` не змінено». У `experiments.log` з'явився рівно один JSON-рядок із `diff_summary`, `ts` і вердиктом. Якщо `strategy.md` у теці не було — його створено як базовий стан.
**Чому це працює без ключа:** proposer і scorer тут — детерміновані фікстури, а не LLM. Живий агент підключається пізніше, контракт при цьому не змінюється.

Далі — власне стартовий шаблон:

1. Відкрийте `courses/AI_Agents_Engineering/lectures/week6/Day12_Self_Improving_Agents_Demo_Day/labs/` і виконайте `go mod tidy`.
   **Чекпойнт:** команда завершується без помилок.
2. Створіть поряд із `main.go` файл `strategy.md` (хоч би один рядок — це ваш «нульовий» стан стратегії; без нього шаблон свідомо падає з помилкою `створіть strategy.md поряд із бінарником`).
3. Запустіть `go run . console` і введіть будь-який дослідницький запит.
   **Чекпойнт:** у відповіді видно `Чернетка звіту з 2 джерел…` — обидві гілки fan-out (`web_search`, `kb_search`) пройшли через `JoinNode` до `draft_report`.
4. Перевірте `cat experiments.log`.
   **Чекпойнт:** з'явився рядок `draft: зібрано 2 гілок` — перший запис вашого майбутнього audit trail.

Далі кожен TODO у шаблоні замінюється на ваші вузли з ДЗ 5–11 — це і є основне завдання.

## Основне завдання

**Ваше завдання —** зібрати фінальний портфоліо-артефакт, стартуючи з [courses/AI_Agents_Engineering/lectures/week6/Day12_Self_Improving_Agents_Demo_Day/labs/main.go](labs/main.go): Personal Research Agent, чиє ядро самополіпшення — ваш `Self-Evolving Coding Agent` на базі multi-critic циклу з ДЗ 11.

### 1. Зшивка (повний конвеєр)

`запит → план (координатор, ДЗ 10) → паралельний збір (пошук/retrieval по вашій базі знань із ДЗ 5–6, fan-out + `JoinNode`) → чернетка звіту → цикл критиків (ДЗ 11) → HITL-затвердження → фінальний звіт`. **Жодних скорочень**: кожен крок має бути у графі, у event log, у тестах.

### 2. П'ять принципів `autoresearch`, застосовані до самополіпшення

- **(а) Обмежена поверхня змін** — агент редагує **рівно один** файл: `strategy.md` (власна дослідницька стратегія: як шукати, скільки джерел, як цитувати, у якій послідовності викликати критиків). Каталог `experiments/` — для дискардів. Усе інше (код агента, дані, конфіги, eval-скрипти) — **read-only**, перевірено `sandbox.IsMutable()`.
- **(б) Фіксований бюджет** — `maxAttempts` ітерацій самополіпшення (рекомендовано 20) у тестованому control loop; eval-вузол має `workflow.NodeConfig{Timeout: 60 * time.Second}`. Це явний hard stop, не «поки що».
- **(в) Єдина метрика** — власний eval-набір із **≥5 дослідницьких питань** з очікуваними фактами; `score = частка знайдених фактів`. Метрика — **об'єктивна й порівнювана** (verifiability constraint з лекції). Без неї — патерн не працює.
- **(г) Стратегія — окремий людино-читний артефакт** (`strategy.md`), який **ВИ** редагуєте в PR. Це — ваш control point, не пост-фактум аналіз.
- **(д) Повний лог** — кожен експеримент (стара стратегія, нова стратегія, метрика до/після, вердикт keep/discard, `git SHA`, `duration_sec`) у `experiments.log`. **І keep, і discard** — compliance хоче бачити, **чому ви не покращили**, так само, як і **як ви покращили**.

### 3. Прогін і демонстрація ефекту

- **≥5 ітерацій самополіпшення** на вашому eval-наборі.
- **Між ранами** вручну відредагуйте `strategy.md` (наприклад, додайте правило «пріоритезувати джерела з ДЗ 6» або «після 3 невдалих спроб — зупинитись і попросити HITL»). У `experiments.log` покажіть, що зміна `strategy.md` **дійсно змінила поведінку** агента (різні джерела, інший порядок критиків, інший фінальний звіт).
- Запустіть агента **з вашою фінальною стратегією** на новому eval-наборі (не на тому, що тренували) і покажіть, що generalization працює.

### 4. README «Чому це безпечно»

README має містити:

- **П'ять розділів**, по одному на кожен принцип `autoresearch`, із посиланням на конкретний файл / вузол / event log.
- **Розділ «Що цьому агенту ще бракує до продакшну»**: ізоляція (sandboxing), ідентичність (SPIFFE / agent auth), durable execution (Temporal) — усі три **за межами цього курсу**. Чітко поясніть, **чому саме ці три шари необхідні в продакшні**.
- **Позначка «станом на вересень 2026»** на версіях (`go 1.27`, `google.golang.org/adk/v2 v2.4.0`, модель провайдера, дата створення eval-набору).
- **Інструкція з відтворення** одного повного рану самополіпшення (10 рядків: клонувати, `cp .env.example .env`, заповнити ключ, `go run ./cmd/research --self-improve --eval=eval/ --strategy=./strategy.md`).

### 5. Метрика якості (окремий розділ)

Зберіть eval-звіт:

- **Базовий прогін** (стратегія v1) vs **фінальний прогін** (стратегія після N ітерацій) — таблиця з 5+ питань.
- **Метрика** = `tests/facts_found`. Скільки зросла — і головне **які типи фактів** знаходяться краще (точні цитати, дати, імена, чисельні значення).
- **Generalization**: запустіть на 3 нових питаннях, яких не було в eval-наборі. Покажіть, що стратегія не overfit-нулась.

## Альтернативні теми (на вибір)

Та сама механіка (повна зшивка + 5 принципів `autoresearch`), інший домен:

- **Security:** Security Research Agent — щотижневий звіт по CVE вашого стеку: збір → перевірка по базі знань → критики (повнота/хибні спрацювання) → HITL; самополіпшення стратегії тріажу вразливостей. Метрика: «% CVE, для яких правильно визначено severity».
- **Research:** класичний Research Agent по вашій професійній темі (наприклад, agentic AI, observability, supply chain) з автоматичним оновленням бази знань. Метрика: «% знайдених ключових фактів із golden-списку».
- **Fun:** Trip Research Agent — досліджує напрямок подорожі (візи, сезон, бюджет, маршрути) і покращує свою стратегію планування за оцінками eval-набору «ідеальних маршрутів». Метрика: «% обов'язкових точок маршруту, які agent знайшов і правильно проранжував».

Усі альтернативи оцінюються за тими самими критеріями, що й основне завдання.

## ++ Advanced (до 20 балів, для сеньйорів)

- **Паралельні воркери самополіпшення**: кілька варіантів стратегії оцінюються конкурентно (`errgroup` + ізольовані git worktree), перемагає найкращий score; порівняйте швидкість збіжності з послідовною версією (зазвичай 2–3× швидше до першого keep-а).
- **Розширене демо**: понад обов'язковий 3-хвилинний скрінкаст (він — у «Формат здачі», не тут) — живий слот із Q&A або другий скрінкаст із навмисно вимкненим гальмом. Обидва варіанти описані в [Demo_Day.md](Demo_Day.md) §7.

## 🔥 Бонус-трек (не оцінюється, не потрібен для сертифіката)

Два виклики з лекційного 🔥 бонус-треку — той самий артефакт, глибший зріз. **Не оцінюються, не потрібні для сертифіката** — це матеріал для тих, кому базовий цикл здався простим:

- **Multi-objective metric (з лекції)**: додайте secondary gate (наприклад, «readability звіту не впав більше ніж на 5%»), покажіть, що composite score зберігає обидва критерії.
- **Post-mortem шаблон**: коли ітерація завершується discard-ом після promising candidate, заповніть post-mortem і додайте в `experiments.log`. Failure — це дані, вони auditable так само, як і success.

## Якщо щось не працює

- **`loadStrategy: створіть strategy.md поряд із бінарником`** — шаблон свідомо відмовляється стартувати без стратегії (принцип (г): стратегія — окремий артефакт). Створіть `strategy.md` у каталозі, з якого запускаєте `go run .`.
- **`go run . console` падає на етапі збірки** — перевірте `go version` (потрібно **≥ 1.27**: директива `go 1.27` у `courses/AI_Agents_Engineering/lectures/go.mod`) і повторіть `go mod tidy`; більшість помилок компіляції в зшивці — це розбіжність типів вузлів (вхід наступного вузла має збігатися з виходом попереднього).
- **LLM-вузли повертають помилку авторизації** — заглушки шаблона працюють без ключа; реальні LLM-критики і синтез потребують `.env` з ключем провайдера. Для `go test ./...` LLM-критики мають бути в mock-режимі (див. чек-ліст рецензентів).
- **`experiments.log` порожній після рану** — переконайтеся, що ваш logger викликається і на keep, і на discard, і що ви не перезаписуєте файл замість append (`os.O_APPEND|os.O_CREATE`).
- **`TestIsMutable` червоний** — див. FAQ №17: точне порівняння для `strategy.md`, `strings.HasPrefix` для `experiments/`, нормалізовані шляхи.

### Що перевірятимуть рецензенти (чек-ліст)

- [ ] `sandbox.IsMutable()` повертає `true` тільки для `strategy.md` і `experiments/`; існує unit-тест.
- [ ] `maxAttempts` реалізовано в детермінованому control loop (не в LLM-підказці); тест доводить зупинку рівно на межі, а `NodeConfig.Timeout` захищає кожен eval-вузол.
- [ ] Eval-набір ≥5 питань має **розмічені очікувані факти** (або повний текст, або golden-список ключових фактів); `metric.Score` — чиста функція без LLM-виклику.
- [ ] `experiments.log` має ≥5 записів; кожен — JSON-line з полями `prev_metric`, `new_metric`, `verdict`, `diff_summary`.
- [ ] `strategy.md` змінювався **між ранами** хоча б один раз; `git log strategy.md` показує коміти людини й агента.
- [ ] README має розділ «Що бракує до продакшну» з трьома пунктами (sandboxing, SPIFFE, Temporal).
- [ ] `go build ./...` і `go test ./...` проходять без API-ключа (metric-функція чиста, LLM-критики — у mock-режимі для тестів).
- [ ] **Скрінкаст (залік/доопрацювання, без балів):** відео доступне за посиланням, у кадрі показано `experiments.log`, названо базову й фінальну метрику. Три механічні підстави для «на доопрацювання» — у [Demo_Day.md](Demo_Day.md) §5; темп подачі й розмір дельти метрики підставою **не є**.
