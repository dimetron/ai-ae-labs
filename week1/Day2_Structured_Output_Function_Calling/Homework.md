# Практичне завдання 2 — Перший власний інструмент: типи проти хаосу

## Легенда

Ваш стажер із ДЗ 1 уже вміє шукати в інтернеті, але все, що він повертає, — це вільний текст. Довіряти йому гроші чи дані поки не можна. Цього разу ви даєте агенту перший **власний типізований інструмент**: Go-функцію зі строгими структурами, де системний код або отримує валідний тип, або бачить явну помилку. Цей самий контракт стане записом майбутньої AI Wiki.

> **Мінімум для старту.** Базовий шлях не потребує іншого провайдера, складного workflow чи ручного JSON Schema: у шаблоні вже є offline fixture і приклад `functiontool.New`. Спочатку запустіть його; потім змінюйте один контракт за раз.

> **Перші 15 хвилин.** Перейдіть у папку стартової лаби й виконайте `go test ./...`. Не редагуйте код, доки не побачите зелений тест: він показує, що schema-описаний tool або передає типізований `RateInput` handler-у, або повертає конкретну помилку. Для цього кроку не потрібні API-ключ і мережа.

Опора для рішення «repair чи fail»: [OpenAI — Structured Outputs](https://platform.openai.com/docs/guides/structured-outputs). Схема доводить форму; дозвіл на ризиковану дію перевіряється окремо.

## Ранній win: перший видимий результат за ≤15 хвилин

Перш ніж писати власний контракт — подивіться, як межа системи ловить зіпсований виклик і **каже вголос, що саме з ним не так**. Ключ і мережа не потрібні.

Спершу переконайтесь, що базовий тест зелений (врізка «Перші 15 хвилин» вище). Далі покладіть у папку лаби файл `earlywin_test.go` — це навмисно зіпсована «відповідь моделі», яку ви пропускаєте через ту саму валідацію, що й справжній tool-call:

```go
package main

import (
	"context"
	"encoding/json"
	"testing"
)

func TestEarlyWin(t *testing.T) {
	raw := []byte(`{"base": "US1", "target": "UAH"}`)

	var in RateInput
	if err := json.Unmarshal(raw, &in); err != nil {
		t.Fatalf("JSON не розібрався: %v", err)
	}

	_, err := Convert(context.Background(), &FixtureProvider{
		Rates: map[string]float64{"USD": 41.5, "EUR": 45.0},
		Date:  "2026-07-29",
	}, in)
	if err == nil {
		t.Fatal("очікували помилку, а валідатор пропустив зіпсований виклик")
	}
	t.Logf("валідатор відхилив виклик: %v", err)
}
```

Запустіть:

```bash
cd courses/AI_Agents_Engineering/lectures/week1/Day2_Structured_Output_Function_Calling/labs
go test -run TestEarlyWin -v .
```

Очікуваний вивід:

```text
=== RUN   TestEarlyWin
    earlywin_test.go:24: валідатор відхилив виклик: invalid currency code: "US1" must be three letters (ISO 4217)
--- PASS: TestEarlyWin (0.00s)
```

Зверніть увагу на дві речі. Перша: JSON **валідний** — `json.Unmarshal` не поскаржився. Друга: виклик усе одно не пройшов, і помилка називає конкретне значення (`"US1"`), а не «bad request». Саме цей рядок побачить модель, і саме за ним вона зможе виправити власний виклик. Це і є вся сьогоднішня теза в одному прогоні: валідний JSON ≠ валідний виклик.

## Основне завдання

**Ваше завдання —** розширити стартовий шаблон [courses/AI_Agents_Engineering/lectures/week1/Day2_Structured_Output_Function_Calling/labs/main.go](labs/main.go) до `Strict Schema Enforcer`:

1. Реалізуйте типізований інструмент курсу валют через `functiontool.New`: вхід `RateInput{Base, Target}`, вихід `RateOutput{Rate, AsOf}` — з `json`-тегами та **описами** полів у `jsonschema`-тегах. У pinned лабі тег не задає `required`/enum: такі обмеження робіть явною `InputSchema` або доменною валідацією. Джерело даних — публічний API (наприклад, НБУ) або чесний мок.
2. Додайте валідацію входу всередині інструмента: невідомий код валюти → зрозуміла помилка (`fmt.Errorf`), яку модель бачить і виправляє свій виклик.
3. Ускладніть вихідну структуру до мінімум 3 рівнів вкладеності з масивом та enum-полем (наприклад, `RateOutput` → `[]HistoricalPoint` → `Source{Kind: "api"|"cache"|"mock"}`) — схема генерується автоматично з Go-структур.
4. Задокументуйте у README 3 діалоги: коректний запит, запит із помилковою валютою (агент самовиправився), запит двох конвертацій в одному повідомленні.
5. Додайте короткий розділ README «Prompt vs Contract»: 3–5 речень, чому добра інструкція агента потрібна, але не замінює JSON Schema, validation і typed tool result.
6. Додайте один рядок «MCP пізніше»: поясніть, чому в цьому ДЗ tool локальний у Go-коді, а MCP буде зовнішньою tool boundary у наступних тижнях. Назвіть `inputSchema`/`outputSchema` та правило: MCP-сервер валідує input до виконання й санітизує output; A2A — це вже agent ↔ agent, не інша назва MCP. Це пояснення, не частина core path.
7. Додайте мінімальний fail path: якщо інструмент не може виправити аргументи після зрозумілої помилки, система має чесно повернути помилку/уточнення, а не вигадати курс. У README покажіть один такий сценарій або поясніть, як він обробляється.
8. Додайте Week 2 bridge: 3–5 рядків псевдокоду або короткий фрагмент README, як `RateInput`/`RateOutput` стануть `InputSchema`/`OutputSchema` вузла workflow-графа ADK. Запускати повний workflow node у Week 1 не потрібно.

## Альтернативні теми (на вибір)

Та сама механіка (типізований `functiontool` + валідація + вкладені структури), інший домен:

- **Security:** інструмент-аудитор `go.mod` — приймає текст go.mod, повертає типізований звіт: список залежностей, версії, поле `Risk: "ok"|"outdated"|"unknown"`.
- **Research:** інструмент метаданих arXiv — за ID статті повертає структуру: назва, автори (масив), категорії (enum), рік.
- **Fun:** інструмент прогнозу погоди для планувальника вихідних із ДЗ 1 — координати → структурований прогноз по годинах.

## ++ Advanced (до 20 балів, для сеньйорів)

- Цикл «валідація → ремонт → повторна валідація» з конфігурованим лімітом спроб + fault-injection тести: ≥3 сценарії невалідних викликів (відсутнє поле, неправильний тип, невідомий enum).
- Порівняйте автогенерацію схеми з Go-структур проти явної `functiontool.Config.InputSchema` — 5 речень у README: коли яка доречна.

## 🔥 Бонус-трек (не оцінюється, не потрібен для сертифіката)

- **Schema-міграція без ламання.** Додайте до `RateOutput` нове опційне поле (наприклад, `Note string`), задокументуйте в README, як старий виклик працює з новою схемою і навпаки — 3–5 речень про те, чому enum-поля мігрувати важче за опційні. Балів не дає; робиться для себе.

## Якщо щось не працює

| Симптом | Що перевірити |
|---|---|
| `go test ./...` червоний одразу після клонування | Ви не в папці лаби: `cd courses/AI_Agents_Engineering/lectures/week1/Day2_Structured_Output_Function_Calling/labs` і повторіть. Для тестів **не потрібні** API-ключ і мережа. |
| Агент відповідає текстом, але не викликає інструмент | Перечитайте `Description` інструмента: модель вирішує «викликати чи ні» саме за описом (див. Лекцію, «Контракт функції»). Опис має казати, *коли* викликати і коли перепитати. |
| «Помилка: невідомий код валюти» | Це не поломка, а робочий fail path: інструмент навмисно повертає зрозумілу помилку замість вигаданого курсу. Задокументуйте цей діалог — він потрібен у README. |
| Немає ключа або мережі для живого API НБУ | Запускайте з фікстурою: `go run . -offline console` — цього достатньо для всього core path. |
| Модель повертає «майже валідний» JSON у діалозі | Переконайтеся, що дані йдуть через tool-call (`functiontool.New`), а не через парсинг тексту відповіді: у core path системний код бачить лише типізований `RateInput`/`RateOutput`. |

Якщо жоден рядок не допоміг — опишіть симптом на форумі вебінару: точна команда + повний текст помилки.
