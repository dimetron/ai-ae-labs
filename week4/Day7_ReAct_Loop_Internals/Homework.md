# Практичне завдання 7 — ReAct зсередини: цикл руками vs цикл у графі

**Тиждень 4, частина 1 · Дедлайн: два тижні від відкриття завдання**

> **Станом на 09/2026:** лаба збирається з `google.golang.org/adk/v2` **v2.4.0** (пін у `courses/AI_Agents_Engineering/lectures/go.mod`) і Go 1.27.

## Легенда

Ваш агент LEDGERWORKS досі виконує лінійні конвеєри: `prepare → tool → format`, як на Вебінарі 3. Але справжнє розслідування — це **цикл**: подумав → пошукав → подивився на результат → уточнив запит → пошукав знову. А CEO (той самий, що на Вебінарі 6 дивився на Agentic GraphRAG) цього тижня хоче, щоб агент сам обирав, який інструмент викликати, без фіксованого графа.

Ірина Дацюк приходить у четвер у канал і просить: *«Напишіть цикл двічі — спершу руками, потім у графі. Хочу бачити, де наша відповідальність, а де — рушія. І **будь ласка**, додайте жорсткий ліміт ітерацій, бо в нас вже був 3 AM-сценарій на $400».*

## Ранній win: перший видимий результат за ≤15 хвилин

Перш ніж писати власний цикл, подивіться на чужий — той самий, який ви сьогодні розбиратимете. Еталонний прогін не потребує ані API-ключа, ані акаунта провайдера, ані мережі: планувальник у мануальній версії rule-based, «модель» у графовій — скриптована.

```bash
cd courses/AI_Agents_Engineering/lectures
go run ./week4/Day7_ReAct_Loop_Internals/labs/solution
```

Перший блок виводу — один повний оберт циклу, розписаний рядок за рядком:

```
=== 1. Мануальний цикл (react.go, без ADK) ===
  [1] thought: Check the runbooks and the merchant payouts at the same time; the two reads do not depend on each other
      obs [c1] search_internal_wiki: 3 hits: event-1 (rejected), event-2 (merged into incident #418), event-3 (open)
      obs [c2] get_merchant_payouts: 2 payouts pending since 03:10; last settled batch #418 delayed, acquirer says unrelated
  [2] thought: Enough evidence; file a ticket
      obs [c3] create_jira_ticket: LDG-1
  iterations: 3, spent: 9 з 30
```

Назвіть уголос три речі, які ви щойно побачили: **думка** (`thought`) — те, що планувальник вирішив перед дією; **дія** — виклик, позначений `CallID` `c1`/`c2`/`c3`; **спостереження** (`obs`) — те, що повернув зовнішній світ, кожне під своїм `CallID`. Це і є цикл, який ви сьогодні напишете двічі.

Друге, що варто помітити, — блок `=== 2.` друкує `events: 7`. Та сама траса, але зібрана рушієм: у мануальній версії `Trace` ведемо ми, у графовій — ADK.

Це не setup і не частина основного завдання: код уже написаний, ви його лише запускаєте й читаєте. Основне завдання починається з порожнього файлу.

## Основне завдання

**Ваше завдання —** зібрати `Native ReAct Agent Core (Go)` у двох варіантах, стартуючи з [`courses/AI_Agents_Engineering/lectures/week4/Day7_ReAct_Loop_Internals/labs/main.go`](labs/main.go):

1. **Руками (manual ReAct):** безфреймворковий ReAct-цикл у звичайному Go-коді (окремий файл/пакет, наприклад `manual/react.go`). Сигнатура орієнтовно:
   ```go
   func Run(ctx context.Context, llm LLM, tools map[string]Tool, task string) (string, []Step, error)
   ```
   Цикл: Thought → Action → Observation → …, доки `Action == "final"` або не вичерпано `maxIterations`. Контракт кроку має приймати **один або кілька** tool calls; у кожного має бути стабільний `CallID`, а кожне Observation повертається саме до свого `CallID`. Для core можна виконувати їх послідовно, але не можна втратити або переставити результати.
2. **У графі (graph ReAct):** той самий цикл через `workflow.NewDynamicNode[IN,OUT]` + `workflow.RunNode[T]` — дочірній вузол-крок `reactStep` викликається в циклі `for` усередині orchestrator-функції, доки не отримано фінальну відповідь. Скелет уже в шаблоні.
3. **≥2 інструменти в обох версіях**, із типізованим контрактом (наприклад, `search_internal_wiki`, `get_merchant_payouts`, `create_jira_ticket` — на вибір). Без API-ключа — почніть з rule-based логіки в `reactStep` (без LLM): це базовий шлях, який має дати видимий `Thought → Action → Observation` і `ErrMaxIterations` у перші 15 хв. У `++ Advanced` — підключення LLM.
4. **Жорсткий ліміт ітерацій** (константа `maxIterations` ≥ 5) — після вичерпання повертається **явна** `fmt.Errorf("вичерпано ліміт N ітерацій: %w", ErrMaxIterations)`, а не тиха зупинка. Тест на це — обов'язковий.
5. **README** (8–10 речень) з порівнянням: що дає рушій (події, межі вузлів, налаштовані retry/timeout policy, schema-валидація typed tool node), що лишилося на інженері (stop conditions, loop budget, дозвіл дії, кореляція calls/results, idempotency), коли писати цикл руками, коли — у графі. Окремо позначте: незалежні read-only calls можна fan-out-ити, side-effecting calls виконують у явному порядку.

## Альтернативні теми (на вибір)

Та сама механіка (цикл із лімітом + ≥2 інструменти), інший домен:

- **Security:** ітеративний аудитор залежностей — цикл «взяти залежність із `go.mod` → перевірити версію → якщо підозріла, пошукати advisory → перейти до наступної» з лімітом. ≥2 інструменти: `parse_go_mod`, `lookup_advisory_db`.
- **Research:** ітеративний пошук відповіді — якщо retrieval із ДЗ 6 повернув слабких кандидатів, агент переформульовує запит і шукає знову (максимум N спроб). ≥2 інструменти: `vector_search`, `graph_traverse`.
- **Fun:** агент-детектив — вгадує загадане слово через цикл «питання → відповідь так/ні → нове питання» з лімітом 10 питань. ≥2 інструменти: `ask_question`, `update_state`.

Альтернативна тема оцінюється за тими самими критеріями, що й основна.

## ++ Advanced (до 20 балів, для сеньйорів)

Оцінюється понад базові 80 балів — будь-яка комбінація пунктів нижче. Це **не** 🔥 Бонус-трек: той не оцінюється взагалі (див. наступний розділ).

- **Детекція зациклення:** повторний tool call з ідентичними `(action, args)` ≥3 рази підряд перериває цикл достроково, *до* `maxIterations`. Повертає окрему `ErrLoopDetected`. Тест: інструмент, що повертає однакове значення, запускається 5 разів — цикл зупиняється на 3-й ітерації.
- **Бенчмарк обох версій** (`go test -bench=BenchmarkReact`): накладні витрати рушія на ітерацію циклу (фіктивний `reactStep` із `time.Sleep(0)`); порівняння `ns/op` для manual vs graph; висновок у README («граф додає ~X ns/op, що = ~Y%»).
- **Підключення LLM:** заміна rule-based `reactStep` на `NewAgentNode(llmagent.New(...))` (за еталоном `sources/github/adk-go/examples/workflow/dynamic/llm/main.go`). Tool selection — через інструкцію та `llmagent.Config.GenerateContentConfig.ToolConfig.FunctionCallingConfig` (`google.golang.org/genai`). Ліміт ітерацій і детермінований dispatch зберігаються.
- **Безпечний fan-out:** виконайте два незалежні read-only calls паралельно й зберіть Observation за `CallID`; два side-effecting calls залиште послідовними та поясніть порядок у тесті або README.
- **Golden-тест на event log:** для графової версії — `go test -update` створює golden файл, `go test` — перевіряє. Захист від drift-у при майбутніх змінах рушія.

## Якщо щось не працює

Найімовірніші збої й очікуваний вивід на кожному чекпойнті:

| Симптом | Причина | Що зробити · очікуваний результат |
|---|---|---|
| `go run ./week4/Day7_ReAct_Loop_Internals/labs/solution` друкує лише `=== 1. …` і падає з `manual loop: …` | Планувальник повернув крок без `final` і без `calls` | Переконайтесь, що `RulePlanner.NextStep` віддає або `Final: true`, або ≥1 `ToolCall`. Очікувано: `iterations: 3, spent: 9 з 30` і далі блок `=== 2.` |
| Цикл крутиться до ліміту, хоч інструмент повертає дані | Observation не повертається в історію (`AppendObservations` не викликано) | Перевірте крок 4 циклу. Очікувано: другий `thought` згадує `#418` з першого Observation |
| `ErrMaxIterations` не спрацьовує, тест на runaway зависає | `Run` повертає порожній рядок замість `error`, або `Budget.MaxIterations = 0` без нормалізації | `errors.Is(err, ErrMaxIterations)` має бути `true`; `go test -run TestLoopStopsAtIterationLimit ./...` → `ok` |
| `RunNode` → `type mismatch` | Тип-параметр не збігається з `Out` вузла | `workflow.RunNode[StepResult]` для `NewFunctionNode(..., func(...) (StepResult, error))`. Очікувано: `go build ./...` без виводу |
| `go test ./...` зелений, але `go run . console` просить ключ | Ви запускаєте стартер `main.go` зі справжнім LLM замість rule-based кроку | Для core-шляху лишайте заглушку без моделі; LLM — лише в `++ Advanced` |

## Підказки (розкриваються поступово, не підглядайте завчасно)

1. **Якщо `NewDynamicNode` повертає дивну помилку** — перевірте, що `RerunOnResume` не виставлений у `&false`; для нашого сценарію дефолт `&true` потрібен (інакше resume зламається).
2. **Якщо `RunNode` повертає `nil, error` з текстом "type mismatch"** — перевірте, що `[ToolOutput]` (тип-параметр) збігається з реальним `Out`-типом `reactStep`. У generic-коді Go «type mismatch» — це помилка виконання, а не компіляції.
3. **Якщо `maxIterations` не спрацьовує** — перевірте, що повертаєте `error` (а не `string` + `nil`) із `RunNode`. Orchestrator-функція має розрізняти «агент відповів» і «сталася помилка».
4. **Якщо rule-based `reactStep` повертає завжди те саме** — це нормально для тесту `maxIterations`. Головне — щоб `Action` ніколи не дорівнював `"final"`, і тоді ліміт спрацює на 100%.
