# Домашнє завдання 4 — Агент виходить у мережу: HTTP-сервіс і бінарник `FROM scratch`

> **Станом на 09/2026 (перед використанням потрібно перевірити):** пін `google.golang.org/adk/v2` = v2.4.0, Go 1.27 — брати з затвердженого `go.mod` курсу, не `@latest`. Маршрут `POST /api/run_sse` і camelCase-поля `appName` / `userId` / `sessionId` / `newMessage` **звірено дослівно з модулем v2.4.0 13.09.2026** (`server/adkrest/internal/models/runtime.go:24–30`) — точні рядки в [`references.md`](references.md). Базовий образ Dockerfile — `golang:1.27`, той самий, що Go-директива `go.mod` лаби.

## Легенда

Підтримка LEDGERWORKS хоче, щоб бот у каналі `#payments-support` сам відкривав кейс повернення просто з треду. Ваш агент дорослішає: досі він жив у консолі, тепер він має відповідати по HTTP — як справжній сервіс, до якого зможуть звертатися інші програми (а з Тижня 5 — інші агенти).

Security додає дві умови, які й формують сьогоднішнє завдання: **жодних образів із тегом `latest`** і склад runtime має бути перелічуваним. Go дає тут передбачувану форму постачання: один статичний бінарник і малий runtime-поверх. Розмір образу не вгадуємо — **вимірюємо** у вашому README (у наративі курсу Марко отримав ≈15 MB; ваше число буде іншим, і це нормально).

## Ранній win: перший видимий результат за ≤15 хвилин

Запустіть стартовий шаблон і переконайтеся, що процес доступний через мережу, ще до будь-яких змін коду:

```bash
go run .
# В іншому терміналі:
curl -i http://localhost:8080/health
```

**Очікуваний результат:** `HTTP/1.1 200 OK` і тіло `OK`. `/readyz` у стартовому шаблоні ще немає — його ви додасте у кроці 1; коли додасте, `503` без ключа провайдера буде очікуваною поведінкою, а не багом.

## Основне завдання

**Ваше завдання —** обгорнути власного агента з ДЗ 3 у HTTP-сервіс із передбачуваним lifecycle: readiness/liveness, graceful shutdown і статичний контейнер `FROM scratch` з явним тегом.

Доведіть `ADK Agent Service` до production-мінімуму, стартуючи з [courses/AI_Agents_Engineering/lectures/week2/Day4_Agent_as_Service_Deploy/labs/main.go](labs/main.go):

1. Оберніть **власного** агента з ДЗ 3 (граф `prepare → open_refund_case → format`) у REST-сервер через `adkrest.NewServer` (див. вендорований `examples/rest`): API під `/api/`, liveness на `/health`, readiness на `/readyz`. `appName` у запитах має збігатися з ім'ям агента, а не бути довільною назвою.
2. Зробіть SSE-виклик `POST /api/run_sse`: спершу створіть сесію, потім надішліть запит із `appName`, `userId`, `sessionId` і `newMessage` (текст — канонічний запит на повернення, напр. `Мерчант A-114 просить повернення по транзакції txn-2026-07-118845`). У README покажіть потік через `curl -N`, а не лише кінцевий JSON.
3. Додайте graceful shutdown: `http.Server` + `signal.NotifyContext` + `server.Shutdown`. Під час drain `/readyz` має перестати приймати нові запити; активний запит отримує час завершитися в межах явно описаного timeout. Покажіть сценарій SIGTERM в README.
4. Зберіть статичний бінарник (`CGO_ENABLED=0`, рекомендовано `-trimpath -ldflags='-s -w'`) і контейнер `FROM scratch` (multi-stage Dockerfile) **з явним тегом версії, не `latest`** — це вимога Security зі сценарію. Якщо агент звертається до HTTPS-провайдера, явно додайте CA certificates; задокументуйте **виміряний** розмір образу, платформу й команду вимірювання.
5. Задокументуйте щонайменше 4 `curl`-перевірки: liveness, readiness, створення сесії й SSE-запит. Для базового шляху саме ці перевірки є достатніми.

## Альтернативні теми (на вибір)

Та сама механіка (adkrest + graceful shutdown + `FROM scratch`), інший домен:

- **Security:** сервіс-ревʼюер конфігів — `POST` Kubernetes-манифест → типізований вердикт про privileged-контейнери й ліміти (граф із альтернативи ДЗ 3).
- **Research:** сервіс-конспектор — `POST` URL статті → структурована вижимка; перший «мережевий» цеглинка майбутнього Research Agent.
- **Fun:** сервіс-бариста з чеками по HTTP.

## ++ Advanced (до 20 балів, для сеньйорів)

- Стрес-тест паралельних **SSE**-запитів через `k6` або `vegeta`. У таблиці README покажіть конкурентність, успішні запити, TTFB/час до першої SSE-події, повну тривалість, помилки й режим тесту. Для повторюваного вимірювання використайте stub-модель; якщо тестуєте реального провайдера, назвіть це end-to-end виміром і зафіксуйте малий бюджет запитів.
- Зніміть CPU та heap-профілі під навантаженням через локальний `pprof` на `127.0.0.1`; назвіть одне знайдене вузьке місце й не виставляйте `/debug/pprof` у мережу.
- Порівняйте виміряні розмір і cold start образів `FROM scratch`, `distroless` та `alpine`, не змінюючи бінарник. Укажіть, чи потрібен кожному варіанту CA bundle.

## 🔥 Бонус-трек (не оцінюється, не потрібен для сертифіката)

- **Chaos-check готовності.** Увімкніть сервіс, зупиніть його `SIGSTOP` посеред стріму SSE і подивіться, як liveness/readinessprobe (або ваш health-запит) поводиться; опишіть у README спостереження в 3–5 реченнях. Балів не дає; робиться для себе.

## Якщо щось не працює

1. **`POST /api/run_sse` повертає `404`** — сесії не існує: спершу `POST /api/apps/{appName}/users/{userId}/sessions/{sessionId}`, і перевірте, що `appName` збігається з ім'ям агента в `agent.NewSingleLoader`.
2. **`/readyz` віддає `503`** — немає ключа провайдера в середовищі або сервіс уже в режимі drain після SIGTERM; це очікувана поведінка readiness, а не баг.
3. **SSE «не стрімить», відповідь приходить одним шматком** — клієнт буферизує потік: використовуйте `curl -N` і перевірте `Content-Type: text/event-stream`.
4. **Контейнер `FROM scratch` не стартує** — бінарник зібрано без `CGO_ENABLED=0` або динамічно злінковано з libc; перезберіть статично й перевірте шлях до executable в `ENTRYPOINT`.
5. **HTTPS-виклик провайдера падає всередині контейнера** — у `FROM scratch` немає CA bundle: скопіюйте `ca-certificates.crt` із build-етапу, як у Dockerfile лекції.

## Критерії оцінювання

| Критерій | Бали |
|---|---|
| REST-сервіс через `adkrest` навколо власного агента з ДЗ 3 | 30 |
| Liveness + readiness + graceful shutdown (з демонстрацією в README) | 20 |
| Контейнер `FROM scratch` з явним тегом версії, статичний бінарник, виміряний розмір і явні CA-залежності | 20 |
| README: 4 curl-перевірки, інструкція збірки | 10 |
| ++ Advanced (бонус) | 20 |
| **Разом** | **100** |

Базове завдання дає до 80 балів; **++ Advanced** — це **+20 додаткових балів** (разом 100); для сертифіката він не обов'язковий. Альтернативна тема оцінюється за тими самими критеріями. Бали за всі 12 завдань підсумовуються: від 60 % відкривається генерація сертифіката, від 85 % — з відзнакою.

## Формат здачі

GitHub-репозиторій з кодом, Dockerfile та README; `go build ./...` має проходити; посилання на репозиторій — у форму здачі. Якщо репозиторій закритий — додайте акаунт ментора в collaborators (акаунт указано в інструкції до курсу на платформі).

Якщо ви починаєте саме з шаблону без `go.mod`, спершу створіть модуль у **своєму** репозиторії, зафіксуйте затверджений для курсу pin ADK Go v2 і лише тоді запускайте збірку:

```bash
go mod init github.com/<ваш-акаунт>/adk-agent-service
go get google.golang.org/adk/v2@v2.4.0    # курсовий пін станом на 09/2026
go mod tidy
go build ./...
```

`v2.4.0` — це пін курсу **станом на 09/2026** (звірено 13.09.2026 проти `courses/AI_Agents_Engineering/lectures/go.mod`). Не пишіть `@latest`: між вашою збіркою і збіркою перевіряючого може вийти нова мінорна версія, і тоді «в мене працює» перестане бути аргументом. Якщо викладач оголосив новіший пін — беріть його, але так само явним числом.
